# 写 PRD

## 先判断

- 用户只是在讨论需求、问问题，不要生成文档。
- 用户要会议纪要、调研报告、交互原型，不要用本技能。
- 用户要新建或重写 PRD / 需求文档 / 需求说明 HTML，按下面流程。

## 流程

1. 在仓库根目录运行：

   ```bash
   node plugins/kocard-prd/scripts/new-prd.mjs "文档标题"
   ```

   脚本会复制 `templates/prd/prd-template.html`，按 `YYYY-MM-DD-标题.html` 命名，并填好标题和日期。不要从零写 HTML，不要手写文件名，不要覆盖已有文件。

2. 只编辑生成出来的副本：
   - 不要改 `<style>` 和 `<script>`，不要加外链字体、CSS、JS。
   - 不要加 logo、品牌字标、点阵背景、卡片阴影、彩色胶囊。
   - 不要加「数据与接口」字段表，也不要默认加「AI 评测」。接口字段放工程文档；AI 功能需要评测时单独补表。
   - 保留模板的章节顺序、class 和表格结构；不适用的章节整节删掉，不留空标题。问题、目标、功能需求、验收是必填章节，不能删。

3. 内容按模板填：
   - 先判断功能是否已上线：已上线就写增量，只写这次新增或变更的行为；通用状态（权限、暂停、断连、空间不足、同名文件）和通用验收不写，先对照代码确认哪些已经存在。
   - 问题写清楚谁、在什么场景、现在怎么解决、为什么不够好；证据不足就标“这是假设”。
   - 目标写结果；非目标只写这期真不做的事，不写现状本来就成立的项。
   - 需求带 P0 / P1 / P2 和可测试的验收标准；数量写清单位（按照片 / 按文件）；P1 要能回答“不做会怎样”，只是把内部统计展示到界面上的不写。
   - 状态与异常按 状态 / 触发条件 / 用户看到 / 如何处理 写，只列与本次改动相关的状态。
   - 验收用 编号 / 前置条件 / 操作 / 预期结果，不写优先级；每条只写外部能观察或操作到的结果（目录里有没有文件、完成数、任务状态），不写“记录里能查到”“标记为”这类测试看不到的内部状态，也不写“体验流畅”这种形容词。
   - 待确认问题写谁回答、是否阻塞。
   - 删除章节后重排 section-kicker 编号（01、02…），并确认左侧目录没有指向已删章节的锚点。

4. 交付前在仓库根目录运行：

   ```bash
   node plugins/kocard-prd/scripts/check-prd.mjs "生成的文件.html" --strict
   ```

   有错误就修，有警告也修完再交付。检查会对比模板的样式块，改过样式一定不过。

5. 报告结果时只说文件路径、还有哪些待确认，不要把整篇文档贴回对话。

## 版本

- 内容变更（需求、状态、验收、范围）升版本，并在变更记录加一行。
- 只改表头、删列、文档状态、排版这类格式调整，不升版本，也不记变更。

## 模板维护

- 只改 `templates/prd/prd-template.html`，不要在某一份 PRD 里改样式。
- 改模板后把顶部 `<!-- prd-template:v5 -->` 的版本号加一，并同步更新插件 README。
- 模板改动只影响之后新建的文档，已交付文档不自动迁移。
