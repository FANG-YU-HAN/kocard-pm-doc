实况照片
是两个文件

相册备份的下一个改动：把静帧和配对视频一起备份，再原样导回系统相册。

看用户流程

两个文件，一个编号

实况不是一种格式。它是一张静帧、一段 3 秒视频，两份原始资源里写着同一个编号。相册靠这个编号把它们认成一张。

HEIC 2.8 MB
IMG_4821.HEIC
静帧。你看到的那一帧。
MOV 3.1 MB
IMG_4821.MOV
配对视频。前后各 1.5 秒，带声音。
配对编号 8F3C2A7E-4B1D-4E9A-9C62-1A5D0B72A21D

编号在文件里，不在文件名里。改文件名、换硬盘、换手机，它都还在。

按住，看看少了什么

切到「两个文件都在」，按住照片。松开就停。

现在只有静帧，按住也不会动。

示意：动的那 3 秒来自 MOV，静帧本身不会动。

备份完成，实况没了

现在的备份只写了一个资源。写入成功，任务打勾，用户以为一切都在。

备份单张照片时，代码从资源列表里挑出第一个匹配的资源，写进硬盘。

实况有静帧和配对视频两份。配对视频的类型是 .pairedVideo，不满足下面的筛选条件，于是被跳过了。

跳过后，写入仍然成功，任务仍然记为完成。用户看不到任何异常。

// 只取一个资源

    for: resource,
    toFile: fileURL,

.pairedVideo 不满足筛选条件，配对视频被跳过。任务仍然记为完成。

看不出来 备份结束仍是 100%，界面不会报错。
播不出来 回导后只剩静图，动的 3 秒和声音没了。
补不回来 旧任务只记录本地编号，缺了哪份说不清。

这是数据正确性问题，不是体验优化。

给开发的硬规则

只有三处差异：枚举资源、同一次请求、读回验证。其他流程不动。

枚举所有资源

实况有 .photo 和 .pairedVideo 两份。两份都写成功，才允许标记完成；任何一份失败，清理已经写下的半份文件。

同一次请求

回导用 PHAssetCreationRequest.forAsset()，把两份资源加进同一个 performChanges，再设置拍摄时间和位置。

读回验证

从 placeholder 拿到新照片，检查 mediaSubtypes.contains(.photoLive)，再实际播放一次。不要以「硬盘上有文件」作为完成标准。

回导 · 关键片段
// 两份资源必须在同一个 request 上
try await PHPhotoLibrary.shared().performChanges {
    let request = PHAssetCreationRequest.forAsset()
    request.creationDate = creationDate
    request.location = location

    let photoOptions = PHAssetResourceCreationOptions()
    photoOptions.originalFilename = "IMG_4821.HEIC"
    request.addResource(with: .photo,
                        fileURL: heicURL,
                        options: photoOptions)

    let videoOptions = PHAssetResourceCreationOptions()
    videoOptions.originalFilename = "IMG_4821.MOV"
    request.addResource(with: .pairedVideo,
                        fileURL: movURL,
                        options: videoOptions)
}

// 写入后读回，确认系统把它认成实况
let subtype = createdAsset.mediaSubtypes
guard subtype.contains(.photoLive) else {
    // 记为失败，不静默通过
}
不要
  • 不要把照片读成 UIImage 再写盘，这一步只会拿到静帧，配对视频不会跟过来。
  • 不要只取 resources.first，配对视频是独立的一份资源。
  • 不要分两次 performChanges，结果会变成一张照片加一段视频。
  • 不要用 localIdentifier 做跨设备去重，换机后会变。
  • 不要同名直接覆盖，先比对内容再决定跳过或改名。

验收只看相册

硬盘上有两个文件不算完成。相册里长按能播，才算。

3.0s

长按能播满 3 秒，封面帧正确。

一张

系统识别为一张实况，不是「照片 + 视频」两条。

有声

声音轨还在，不是静音播放。

原位

拍摄时间和地点回到时间线原处。

iCloud

原片只在云端，也能完整备份和还原。

0

中断、拔盘、退后台，硬盘上不留半份文件。

还没拍板的三件事

下面是建议和代价。你拍板后，我把结论写回需求。

编辑过的实况 裁剪、调色、换封面后，回来是哪一版？ 建议：先还原原片

MVP 先还原原始静帧和配对视频，结果页写明「编辑效果未还原」。

代价：用户裁剪、调色、换过封面帧后，回导看到的是原片。

回导范围 第一版做到什么范围？ 建议：多选 + 整个任务

支持多选和整个任务，单张入口留到下一版。

代价：多做一层选择界面和去重逻辑，工期需要研发评估。

老的半份数据 旧版本留下的实况怎么补？ 建议：上线就扫描，一键修复

上线即扫描历史备份，标出不完整的实况，提供一键修复。

代价：上线初期要跑一轮全盘扫描；原片已从相册删除的，补不回来。

另外三项（备份清单、同名冲突、目录兼容）在需求全文附录 B。

备份的不是一张照片，是一组资源和一个关系。

回导也一样：不是写两个文件，是让系统把它们认回一张实况。
